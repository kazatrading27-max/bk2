# 2026-10-18

## Fixed missing TLS certificate on mebakgtl.com (Yegara shared hosting / DirectAdmin)

**Symptom:** live site showed a certificate error. HTTPS was served but with the shared
server cert `CN=lu-shared01.dapanel.net` (name mismatch) because the domain had no cert.

**Root causes (both host-level, provider side):**
1. DA ACME preferred a wildcard (`*.mebakgtl.com`) → forced DNS-01 → lego publishes TXT
   via DA's local DNS then waits 5 min for propagation; the remote authoritative NS
   (ns5/ns6.private-nameserver.net) sync slower, so every attempt failed (~12 min each).
2. Server's own resolvers `107.189.0.68/69` return **SERVFAIL** for `mebakgtl.com`
   (`getent hosts` fails on the box) while public DNS resolves fine → DA's HTTP-01
   pre-check rejects all hostnames ("HTTP request does not reach this server").
3. `/.well-known/acme-challenge/` is intercepted by DA → served from root-owned
   `/var/www/html/.well-known/acme-challenge/`, so userland HTTP-01 is impossible.

**Fix applied:**
- Installed acme.sh in userland (`~/.acme.sh`), issued via DNS-01 manual mode.
- Published the TXT records through the DirectAdmin panel (DNS API via the authenticated
  browser session: `POST /CMD_API_DNS_CONTROL`). Propagation to ns5/ns6 took seconds.
- Key detail: DirectAdmin would not accept a foreign private key (`Unable to find key`
  / `key values mismatch`). Solution was to read DA's own key via
  `GET /CMD_API_SSL?domain=...&json=yes` (field `KEY`), build a CSR from it, sign that
  CSR with `acme.sh --signcsr`, then paste the resulting fullchain + DA key via
  `POST /CMD_API_SSL` with `action=save&type=paste&certificate=<cert+key PEM>`.
- Result: valid LE cert (SAN mebakgtl.com + www.mebakgtl.com), verify OK, HTTP 200.
  Expires 2027-01-15.

**Panel/API notes worth remembering:**
- Yegara client area is **ClientExec 7.2.2** at my.yegara.com (not WHMCS). Login form
  posts `email` + `passed_password` to `index.php?fuse=admin&action=Login`.
- Package page: `index.php?fuse=clients&controller=products&view=product&id=107431`,
  "Login to DirectAdmin" SSO link uses a per-session `sessionHash` — must be clicked
  in-session, it cannot be reused.
- DA SSL API accepts `certificate` + `privatekey`; `type=paste` (valid types:
  server|create|paste). `type=create` generates a self-signed cert + key and stores the
  key server-side.
- agent-browser sessions do NOT persist between separate Bash invocations — the whole
  login → SSO → action flow must run in one script. Also `https_proxy` env breaks it.
